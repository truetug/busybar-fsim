# FS: хостовая цель прошивки BUSY Bar (`fsim`) — итоговый отчёт

Трек FS, 25–26.10.2026. План — `docs/services/firmware-host-target-spike-task.md`, журнал по частям —
`docs/services/firmware-host-target-spike-fs2-log.md`, кадры и видео —
`docs/services/firmware-host-target-spike-fs2/`. Прошивка — `busy-app/busybar-firmware`, `dev` @ `7afbacbd`,
релиз 1.3.1-rc @ `5d7f3188`.

## Итог в пяти строках

1. **Настоящая прошивка бара работает на x86_64 без единой правки в её коде**: те же furi, LVGL,
   JerryScript, `web_server`, `js_runner`, лаунчер и APPS. Clock, установка приложений по HTTP API бара,
   режимы ручки, диалог Start / Setup — как на баре.
2. **Это уже стенд ревью:** образ `fsim-runtime-recorder` по HTTP отдаёт видео и скриншоты сценария;
   `BarClient` каталога работает против него без изменений.
3. **Наблюдатель за прошивкой** собирает fsim из исходников каждой новой сборки CI, гоняет смоук и
   обновляет теги образов; при поломке остаётся на рабочей версии и поднимает тревогу.
4. **WASM (браузер) — реально, но дорого и не сейчас:** вся прошивка собирается в 1,7 МБ `.wasm`, но
   POSIX-порт FreeRTOS под нагрузкой прошивки даёт недетерминированные сбои, нужен свой порт, плюс
   мост HTTP API и виртуальный диск; около 2–3 недель и постоянная поддержка. Дешёвая замена —
   стрим кадров и ввода с серверного fsim.
5. **Рекомендация:** нативный fsim оставить стендом ревью, предложить команде прошивки взять его
   официальной целью (правки на их стороне — около десятка строк, список ниже), браузер — стримом.

## Сколько стоило

- **Код fsim — около 4 300 строк:** `targets/fsim` 2 022 (16 файлов C: HAL, дисплеи, питание, сеть, ввод,
  заглушки периферии), `tools` 1 463 (генератор приложений, SD, видео, раннер, смоук, наблюдатель,
  оверлей WASM), `runtime` + `recorder` 424, плюс `CMakeLists.txt`.
- **Правок в коде прошивки — 0.** Всё различие — в `targets/fsim` и патчах при сборке:
  - `port.c` POSIX-порта FreeRTOS: переключение откладывается до выхода из критической секции;
  - `dsp.c`: одна функция с ARM-ассемблером заменяется переносимой;
  - `lv_bin_decoder.c`: расширение `"bin"` → `"image"`, как в прошивке;
  - линкером обёрнуты `poll` (ожидание сокета не держит планировщик), `connect` (внешняя сеть
    закрыта), `pthread_sigmask` (сбой не маскируется).
- **Исключено** (подмены или заглушки 501): Wi-Fi, BLE, Matter, USB, SiWG917 / intercom, обновление
  прошивки, звук, яркость и статус-диоды, облако (mqtt), mDNS, TLS.
- **Время:** около трёх рабочих дней активной работы по журналу (FS-1 … FS-5) плюс полдня на FS-3.

## Находки

**Различия платформ** (хост ловит не баги прошивки, а различия с чипом):
- у POSIX-порта FreeRTOS переключение потока происходит сразу, на Cortex-M — после выхода из
  критической секции; `furi_event_flag_set` будил поток посреди своей секции, и хранилище писало в
  освобождённую память;
- холостая задача в POSIX-порту крутится на 100 % ядра (на чипе спит по `WFI`) — хук со сном: 98 % → 11 %;
- ожидание сокета блокировало планировщик.

**32-битные допущения и GCC-специфика прошивки:**
- `static_assert` на смещения в `version.c` и `sizeof(ConnectionContext) == MG_DATA_SIZE` в `web_server_i.h`;
- **вложенные функции GNU C** в `canvas.c`, `anim_file.c`, `anim_file_img.c` — clang их не собирает;
- трюк с регистром `r12` в `core/check.h` — на x86_64 работает, в wasm регистров нет.

**Прочее:**
- сервисы прошивки не должны возвращаться; недостающая запись `furi_record_open` — молчаливое
  зависание (первый признак любой поломки сборки);
- **версии:** у стабильного 1.2.4 API 27.5 и нет `/api/apps/*` (появились в 1.3.0-rc, API 27.14) —
  рекордер на нём работать не может, `stable` сейчас = 1.3.1-rc;
- CI публикует всё нужное: пакеты обновления, `bkp`, `openapi.yaml`; у `dev` коммит зашит в имя
  артефакта, у релиза — по тегу.

## Хрупкость и стоимость поддержки

Изменения за 3 месяца (131 коммит в клоне владельца) в областях, от которых зависит fsim:

| Область | Коммитов | из них в заголовках |
|---|---|---|
| ядро furi, HAL f21, `furi_hal_include`, loader, desktop, input, power | 0–2 | 0–1 |
| storage | 3 | 1 |
| gui | 7 | 5 |
| `js_runner` | 22 | 18 |
| `web_server` | 27 | 17 |
| `js_app` | 8 | 7 |

- **Стабильно:** ядро, HAL, загрузчик, desktop — именно то, что мы подменяем и от чего зависим сильнее
  всего.
- **Меняется:** `web_server`, `js_runner`, `js_app` — их мы берём **из исходников как есть**, поэтому
  они не ломаются сами; ломают новые зависимости на железные сервисы (новый модуль API → вызов
  `sl_info`, `updater`, `matter`…). Это видно на сборке как `undefined reference`, наблюдатель
  поднимает тревогу.
- **Практика:** `dev` (23.10) и 1.3.1-rc (22.10) собрались без правок fsim, но это почти одна и та
  же прошивка (разница в день), так что **устойчивость к обновлениям пока не доказана**. Единственная
  проверка на удалении — стабильный 1.2.4 (11.09): он не собирается, в нём нет части сервисов
  (`js_app_installer`, `apps_menu_on_start`), это другая ветка развития. Настоящий тест — первый
  новый релиз после 1.3.1-rc: наблюдатель покажет, сколько правок он потребует.
- **Оценка поддержки:** новая зависимость на железо = заглушка 20–50 строк, около часа; по
  истории — несколько раз за квартал, а не еженедельно. Нужен человек на тревогу и раз в квартал
  ревизия (новые подмены, лимиты).

## FS-3: оценка WASM (браузер)

**Измерено:**
- **Собирается:** все 452 исходника fsim (LVGL, JerryScript, mongoose, web_server) компилируются
  emscripten 3.1.69 / clang; проблемны три файла с вложенными функциями GNU C и заголовок `check.h` —
  исправлены **оверлеем** (`tools/wasm_overlay.py`, прошивка не меняется), оверлей падает с понятной
  ошибкой, если прошивка изменилась.
- **Размер:** `fsim.wasm` **1,73 МБ** (`-O2`; 5,6 МБ без оптимизации), gzip 599 КБ, brotli 547 КБ, JS-обвязка
  262 КБ. Данные: ресурсы приложений с SD **11,2 МБ** (605 файлов; 13,1 МБ в пакете обновления CI).
  Первая загрузка ≈ 14 МБ, дальше кэш.
- **Потоки:** без `SharedArrayBuffer` страница не запустит прошивку; в Chromium проверено
  (`crossOriginIsolated=false` → `SharedArrayBuffer` не определён; с `COOP: same-origin` +
  `COEP: require-corp` — есть). POSIX-порт FreeRTOS на простом примере (две задачи, задержки по 200 мс)
  работает без правок, тики точные (в node и в браузере).
- **Прошивка целиком — не загрузилась:** образ SD находится, сервисы стартуют, затем сбой. **Три
  запуска одного бинарника дали три разных сбоя** (`xEventGroupWaitBits`, зависание,
  `furi_event_loop_object_subscribe`) — это гонка, а не одна ошибка. Причина: критические секции
  POSIX-порта строятся на маскировании сигналов (`pthread_sigmask`), а emscripten эмулирует сигналы и
  ничего не маскирует. На простом примере незаметно, под нагрузкой прошивки проявляется.
  **Время старта в браузере не измерено** — до конца загрузки не дошло.

**Оценка (не измерено):**
- **Свой порт FreeRTOS для wasm** — детерминированный (один исполняющийся поток по «эстафете», тик
  от таймерного потока, без сигналов) или на волокнах emscripten без `SharedArrayBuffer`: 2–4 дня на
  первую рабочую версию, плюс отладка гонок.
- **HTTP API без сокетов:** приложения ходят на `http://localhost/api/...` через `js_runner` →
  `lib/fetch` → mongoose. Нужен мост: либо виртуальные сокеты внутри процесса, либо прямой вызов
  обработчиков API: 3–5 дней.
- **Виртуальный диск:** раздел backup 256 МБ не хранить (нули + запись в память), ext — из пакета CI
  (≈ 13 МБ), блочное устройство в JS: 1–2 дня.
- **COOP / COEP на сайте каталога:** изоляция нужна всей странице. Сторонние ресурсы и iframe
  (видео-встраивания) без заголовков `Cross-Origin-Resource-Policy` блокируются; вход через GitHub,
  если он идёт полным редиректом (в коде каталога переход на `/login?next=…`), страдать не должен, а
  через всплывающее окно с `window.opener` — будет; способ входа не проверялся. Своё видео и
  картинки из хранилища потребуют CORP-заголовков на шлюзе. **На странице каталога не проверялось**,
  безопасный путь — отдельная изолированная страница бара.
- **Поддержка:** каждая новая версия прошивки — прогон оверлея и порта; нагрузка на батарею и CPU
  зрителя не измерена.
- Итого **2–3 недели до работающей демонстрации** и постоянная поддержка.

**Вывод: «реально, дорого, не сейчас».**

**Альтернатива — стрим с серверного fsim** (рекордер и канал управления уже есть):
- по измерениям: ≈ 115–122 МБ памяти на экземпляр, холостой ход 11 % ядра (в эмуляции amd64 на Apple
  Silicon; на нативном amd64-сервере, по ожиданию, ниже, **не измерено**), запуск до готового API
  6–7 с, кадр переднего экрана 4 608 Б в сыром виде, передаётся только при изменении;
- реализация: WebSocket-шлюз «кадры наружу, ввод внутрь» поверх существующего канала управления,
  лимиты и изоляция уже есть в рекордере: 2–3 дня;
- цена — один процесс на зрителя: сервер с 16 ГБ держит порядка ста одновременных зрителей по памяти
  (оценка), задержка — одна сетевая поездка на нажатие.

## Решение на выбор владельца

1. **Нативный fsim — стенд ревью вместо mockbar.** Уже работает; осталось встроить сторону каталога
   (10.25-9) и решить, куда публиковать образы.
2. **WASM в браузере вместо JS-бара — не сейчас.** Вернуться, если зрителей станет столько, что
   серверный стрим окажется дорогим, или понадобится работа без сервера. Начинать с портирования
   FreeRTOS, потому что это главный риск.
3. **Предложить команде прошивки взять fsim официальной целью** — рекомендую. Главный довод: CI
   уже публикует сборки на каждую ветку, с fsim там же появятся `busybar-fsim-<ветка>` (и позже WASM),
   а виртуальный бар каталога и стенд ревью получат любую версию без нашей сборки. Плюс CI без
   устройств. Что нужно с их стороны (предложение, не PR, около десятка строк):
   - защитить трюк с `r12` в `core/check.h` (`#if` по архитектуре);
   - переписать вложенные функции в `canvas.c`, `anim_file.c`, `anim_file_img.c` на статические;
   - заменить 32-битные `static_assert` на проверки, не зависящие от размера указателя
     (`version.c`, `web_server_i.h`);
   - починить `./fbt build` (устаревшие списки заголовков SDK) — **их баг, виден только при полной сборке**;
   - держать список сервисов-зависимостей `web_server` явным (сейчас часть неявно тянет matter, intercom).
4. **Не идти и остаться на JS-баре — не рекомендую:** расхождения с настоящим баром каталог уже
   ловил руками (кнопка Start, направление колеса, текст режимов).

## Оговорки

- Все измерения нагрузки — в эмуляции amd64 на Apple Silicon; цифры нативного сервера — оценки.
- Образ рекордера собран из `dev` и 1.3.1-rc; на релизах без API приложений (≤ 1.2.4) не работает по
  существу.
- Код fsim не опубликован и лежит локально (GPLv2+; прошивка GPLv2+). Копировать его в репозиторий
  каталога нельзя — каталог видит только HTTP.
